# Private image provisioning and retries

`install-host.sh` is only for the disposable Rocky 9 Packer VM. It requires the actual FIPS kernel and SELinux Enforcing, a detected VM, the locked root account, and the existing `sudo /bin/bash .../install-host.sh` invocation from `packer`. The protected build sudoers rule and the packer-owned private authorized-keys file must match the build recipe. The key must contain one RSA public key of at least 3072 bits. The guard never prints the key or machine identity and never generates credentials.

Before copying payloads or changing service policy, the installer takes an advisory lock on the existing `/etc` directory inode. The sealer uses the same lock. The guard durably writes `/etc/nebulalog/bootstrap/private-build.json`, binding this provisioning transaction to SHA256 fingerprints of the VM machine identity and per-build public key. Its root-owned directories are mode0700; the single-link receipt, unsealed marker and `state` are root:root mode0600. The receipt starts in `provisioning`; `installed` is written only after the whole installer succeeds. Directory entries, file contents and renames are synchronized before continuing.

A retry requires the same VM and key, the exact unconfigured/private state, no enrollment or sealed artifacts, no registered NebulaLog storage mapping/volume group or boot-storage entry, and an empty, unmounted data directory. Unexpected files under the protected appliance/bootstrap directories refuse the retry. Empty bind mounts and mounts below the data path are also refused. Missing ancillary markers may be completed only for an already recorded unfinished provisioning transaction. A completed build with missing markers is refused.

The guard never resets configured state, adopts an old payload without the new receipt, deletes customer data, or repairs malformed receipts. An old installer failure before this guard existed requires explicit recovery review or a fresh disposable build. Preserve its state; do not fabricate a receipt. Changing the build key or VM identity also requires a fresh build or separate reviewed recovery. A root operator can change local files, so this receipt is an accidental-rerun guard and consistency record, not tamper-proof attestation or source provenance.

SELinux registration reads the policy's file-context records before modifying anything. The six fixed registrations in `install-host.sh` are added only when absent; exact matches are no-ops. Different contexts, file types, foreign overlapping equivalences or any unexpected local file-context customization refuse registration. No `semanage -m`, deletion, or fallback that ignores errors is used. This intentionally expects a pristine private build. Read-only inspection of Rocky 9.8's `python3-policycoreutils-3.6-5.el9` RPM verified the `seobject.fcontextRecords` tuple/add/equivalence API used by the guard. This is package-source review, not installed-guest policy execution. [Rocky policycoreutils package](https://download.rockylinux.org/pub/rocky/9.8/AppStream/x86_64/os/Packages/p/python3-policycoreutils-3.6-5.el9.noarch.rpm).

Rocky's distribution `file_contexts.subs_dist` contains the exact substitution `/run /var/run`. Its `seobject.validate()` rejects registrations beneath `/run` and directs callers to the substituted path. When that exact **distribution** alias is present, the guard registers `/var/run/nebulalog-public(/.*)?` as `httpd_var_run_t` and `/var/run/nebulalog-status(/.*)?` as `container_file_t`. Runtime paths and the fixed installer arguments remain `/run/...`; the other four registrations are unchanged. This is a fixed two-expression translation, not general alias resolution. A local alias, a different destination, or a conflicting mapping on either spelling still refuses. The fresh post-write read must confirm the exact committed rule and unchanged runtime alias. [Rocky targeted policy package](https://download.rockylinux.org/pub/rocky/9.8/BaseOS/x86_64/os/Packages/s/selinux-policy-targeted-38.1.75-2.el9_8.noarch.rpm).

`nebulalog-seal` requires the matching completed receipt in both its initial and detached invocations, in addition to the existing bundle/source/provenance checks. Keep Packer `ssh_clear_authorized_keys=false`: the mandatory sealer must verify the build key before removing the packer account and keys itself. The sealer removes the disposable receipt before writing the sealed image marker. SSH remains available in an explicitly unsealed private build until that mandatory seal operation.

The Kickstart public-key decoder accepts exactly one optional terminal LF because the pinned Packer SDK returns `ssh.MarshalAuthorizedKey` output unchanged. URL query encoding preserves that LF as `%0A`; rejecting every newline would abort `%post` even with a valid build key. The decoder removes one terminal LF, rejects remaining controls, duplicate parameters, options/comments, malformed SSH wire fields and RSA moduli outside 3072–8192 bits, then writes one canonical line. It never prints the key. The key format name `ssh-rsa` identifies the RSA public key; it does not enable SHA1 SSH signatures. Primary implementation references: [Packer SDK v0.6.10 public-key serialization](https://github.com/hashicorp/packer-plugin-sdk/blob/v0.6.10/communicator/sshkey/pubkey.go), [Go SSH v0.54.0 terminal LF](https://github.com/golang/crypto/blob/v0.54.0/ssh/keys.go#L301).

Eight targeted Kickstart tests execute the actual embedded Python against synthetic public wire records, covering the terminal-LF transport regression and refusal cases. They do not generate credentials, operate a guest, or prove SSH login. A disposable installer recovered manually after a fatal `%post` remains a diagnostic fixture; release reproducibility requires a fresh successful installation from the corrected, recaptured source.

The installer enables `nebulalog-os-update.timer`. Its service requires the enrolled `/etc/nebulalog/maintenance.json` and the data mount. Outside the configured maintenance window, or with automatic updates disabled, it does no package work. Inside the window, the host controls, actual encrypted storage, repository trust, live database and local authentication checks, and configuration/database backups must pass before DNF. Five targeted activation tests verify that absent/disabled policy, failed preflight, incomplete backups and unhealthy host controls never invoke DNF. Reboot remains separately blocked until encrypted unlock is qualified and explicitly enabled. These are local fixture checks; actual guest timer and update/reboot survival remain release acceptance work.

The installer places the AIDE manager helper at `/usr/libexec/nebulalog/nebulalog-aide` (0755), its policy at `/usr/share/nebulalog/aide/policy.conf` (0644), and the mandatory captured `security/aide.conf` at `/etc/aide.conf` (root:root 0600), followed by `restorecon` on that replaced inode. The managed config points at the canonical encrypted database; no baseline is initialized during image build. Its exact encrypted state context is `/var/lib/nebulalog/manager/aide(/.*)?` with `aide_db_t`; read-only inspection of Rocky 9.8's `selinux-policy-targeted-38.1.75-2.el9_8` RPM confirmed this existing database type. A reviewed baseline must be enrolled after setup and removal of disposable build material. Never infer AIDE coverage from timer enablement; actual baseline/check execution and SELinux access in the guest remain qualification gates. [Rocky targeted policy package](https://download.rockylinux.org/pub/rocky/9.8/BaseOS/x86_64/os/Packages/s/selinux-policy-targeted-38.1.75-2.el9_8.noarch.rpm).

## Frozen source inputs for a clean build

After every source writer finishes, use `prepare_provenance.py` to capture the complete source manifest and initial-release descriptor for the independently verified offline image bundle. Then run the host-only staging helper with that same source and provenance. All destinations below are new, exclusive directories; a partial or previous stage is never adopted or overwritten.

```sh
python3 appliance/packer/prepare_provenance.py \
  --source "$PWD" --bundle /absolute/verified-image-bundle \
  --output /absolute/new-provenance --sequence 1 --schema-revision 1
python3 appliance/packer/archive_sources.py \
  --source "$PWD" --provenance /absolute/new-provenance \
  --output /absolute/new-complete-source.tar
python3 appliance/packer/archive_sources.py \
  --provenance /absolute/new-provenance \
  --output /absolute/new-complete-source.tar --verify-only
python3 appliance/packer/stage_sources.py \
  --source "$PWD" --provenance /absolute/new-provenance \
  --output /absolute/new-frozen-source
python3 appliance/packer/stage_sources.py \
  --output /absolute/new-frozen-source --verify-only
```

Retain the complete source tar, its adjacent `new-complete-source.tar.receipt.json`, and both original provenance documents together. The archive includes exactly every captured source file, including application code, tests, documentation, and build recipes; the installer stage below contains only its runtime subset. The archive helper reads Git inventory and uses protected regular-file descriptors, verifies source bytes against the capture before publication, re-reads all source bytes and checks the complete inventory/Git identity after copying, and validates every canonical tar header, payload, and padding byte. It refuses changed, missing, extra, unsafe, linked, or oversized captured files, known credential/generated path patterns, and PEM private-key header lines. These are targeted exclusions, not an exhaustive secret scan. Ignored local files and Git metadata are never added or read as archive members. The limits are 10,000 Git-listed entries, 128 MiB per source file, and 512 MiB total source bytes; USTAR names must fit the standard's fixed header fields.

Archive members have deterministic sorted names, zero timestamps/user/group IDs, empty owner names, and mode 0644. Source schema v1 binds file bytes, so original permissions are not reconstructed. The final tar and receipt are owned read-only files (0400), published exclusively after verification; existing paths are never overwritten. A failed or interrupted receipt publication may leave a complete tar without an accepted receipt. Preserve such evidence and use a new destination for a new attempt. Always run `archive_sources.py --verify-only` with the original provenance directory before accepting the pair; that check requires no checkout and rejects altered members, extra entries, tar extensions, padding, metadata, receipt types, or hashes. Owner/root writes can still replace read-only files: this is unsigned byte-retention evidence, not tamper-proof attestation, Git history reconstruction, a signature, or proof of a successful build. Keep all source writers paused through capture, archive, and staging; keep output outside the repository or in an already ignored directory. The helper runs no image, guest, or runtime commands.

The staging helper consumes the existing source/provenance schema without rewriting its identity. It verifies the complete repository snapshot before and after copying, selects only installer/runtime inputs, the Keycloak realm template, Kickstart HTTP files and the captured Packer template, and independently re-reads every staged file before publishing `staging-receipt.json`. It excludes application source, test suites, container recipes, Git metadata and ignored local material from the guest payload. Symlinks, unlisted output files, credential/generated paths, private-key material, changed bytes and unexpected modes fail closed. A failure leaves a private incomplete directory without an accepted receipt; review it and choose a new destination for a new attempt.

Use the receipt's absolute `packer_template` and `packer_varfile` paths for the future build. For example, once the separate ISO/private-key/build options and verified image-bundle path are prepared:

```sh
packer build -var-file=/absolute/private-build-options.pkrvars.hcl \
  -var-file=/absolute/new-frozen-source/frozen-sources.pkrvars.hcl \
  /absolute/new-frozen-source/appliance/packer/nebulalog.pkr.hcl
```

The generated varfile explicitly sets `appliance_source_directory`, `keycloak_realm_template`, `kickstart_directory` and a nonsecret `build_disk_id`. The three source-path defaults still point at the live workspace for development compatibility; disk identity has no shared default. Do not override these frozen paths or the recorded identity later in the command. The helper does not stage, pull or verify image archives or the Rocky ISO, supply the SSH private key, sign a release, launch Packer, or operate a guest. Keep the separately verified offline bundle bound to the descriptor's `bundle_manifest_sha256` and copy both provenance documents into that bundle as required by the existing installer contract.

Staged entrypoints are read-only executable files (0500); modules/configuration and metadata are read-only (0400). Directories are private (0700) and retain owner-write permission for Packer file-transfer compatibility. Source schema v1 does not capture file modes, so these modes are fixed by the runtime path contract rather than inherited from the mutable checkout. This protects against accidental edits and verifies consistency; the same user or root can still replace files. Run `--verify-only` immediately before starting Packer, keep the stage untouched for the whole build, and retain its receipt. Fourteen targeted host-only fixture tests and Packer syntax-only validation cover this staging contract; they do not establish a reproducible completed guest build.

Before any file upload, the captured Packer template runs a small preflight as the actual non-root `packer` account. It creates exactly `/tmp/nebulalog-appliance` and `/tmp/nebulalog-image-bundle` with mode0700. An existing destination is accepted only when it is an empty, nonsymlink directory with that account's UID/GID and exact mode0700. Nonempty directories, different ownership/modes, files, symlinks and a preexisting `/tmp/nebulalog-keycloak-realm.json` refuse the transfer without cleanup or permission repair. Every existing target is inspected before missing directories are created; a conflicting creation also refuses. These temporary paths do not replace the installer's separate root/private-build guard.

Both directory sources have explicit trailing slashes, so their **contents** land directly in the prepared targets. This keeps `/tmp/nebulalog-appliance/install-host.sh` and `/tmp/nebulalog-image-bundle/manifest.json` stable under either SCP or SFTP, without relying on SCP's special behavior for a missing destination. The pinned SDK otherwise includes the source basename when the slash is absent. [Packer directory-transfer contract](https://developer.hashicorp.com/packer/docs/provisioners/file#directory-uploads), [SDK v0.6.10 SCP/SFTP implementation](https://github.com/hashicorp/packer-plugin-sdk/blob/v0.6.10/sdk-internals/communicator/ssh/communicator.go#L490).

A partial upload is evidence to inspect, not an empty destination to adopt. Re-running the upload phase against nonempty staging is refused. An installer retry against already transferred, reviewed source still uses the existing protected VM/key receipt and does not require another upload; use a fresh disposable build for a fresh full Packer run. Ten targeted local fixtures execute the actual embedded preflight and check the content-only recipe contract. They do not execute SSH, transfer into a guest, or prove a completed image build.

Each new private build needs a new source stage, which generates and records a 16-hex disk identity. Its OS and data serials are `NL<build_disk_id>OS` and `NL<build_disk_id>DT`: distinct, exactly 20 characters and within VirtIO's device-ID limit. Retain those exact serials for subsequent boots of the same private disks; never reuse a stage for a different VM's new disks. For a manual build without staging, supply a fresh `build_disk_id` explicitly. These are public device identifiers, not credentials. [VirtIO block ID size](https://github.com/qemu/qemu/blob/v9.2.0/include/standard-headers/linux/virtio_blk.h#L57).

The pinned Packer QEMU 1.1.6 plugin has no per-disk serial field and rejects `disk_interface=none`. Its `virtio-scsi` layout produces the existing OS/data file backends with `if=none,id=drive0` and `id=drive1`; the recipe deliberately replaces only the frontend `-device` list with two explicit `virtio-blk-pci` devices carrying those serials and the existing VirtIO NIC. The guest retains `vda`/`vdb`, the 80 GiB/1 TiB capacities, generated image paths, installer CD and loopback SSH forwarding. No `-drive` list is replaced and no global serial is shared across devices. Recheck this mapping before changing the pinned plugin. [Pinned backend and override implementation](https://github.com/hashicorp/packer-plugin-qemu/blob/v1.1.6/builder/qemu/step_run.go#L210).

Three pure recipe/descriptor tests verify serial separation/length, required build identity, unchanged backend/SSH wiring and the VMware disk-ID extension. They do not start QEMU, produce disk images or boot a guest. The next clean guest must still prove two distinct persistent `/dev/disk/by-id` whole-disk paths, nonempty matching `lsblk` serials, blank data-disk eligibility and identity persistence after reboot.
