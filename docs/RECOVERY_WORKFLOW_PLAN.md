# Recovery operator workflow: implementation plan

Source audit: 2026-10-19. This is a proposed implementation plan, not an enabled API, a deployed interface, or recovery acceptance. Only this document was added by the audit. The existing coordinators are changing; implementation must bind to their reviewed final contracts.

The [original specification](SPECIFICATION.md) requires configuration/authentication/PostgreSQL/certificate/security-baseline recovery and optional ClickHouse data. K01–K03 in [RELEASE_ACCEPTANCE.md](RELEASE_ACCEPTANCE.md) remain unchanged. The audit retained all 154 ID/requested-requirement tuples, with SHA256 `1319192bafc148671b29e80261319454530ff5e057ca69168ee6ebc1aa2f42ae` over their ordered compact JSON representation. This plan does not replace that acceptance inventory or waive identity, lifecycle, storage, FIPS, SELinux, performance, or failure-recovery requirements.

## Operator flow to implement

**Running appliance:** an Administrator opens Backup & recovery, selects an enrolled public recipient certificate and configuration-only or explicitly selected full logs. The page shows measured required/free space, arrival reserve, estimated phase times, maintenance impact and exact immutable recovery compatibility. The operator reviews the plan, performs qualified fresh MFA, and accepts that exact plan. Return a durable job ID before dispatch. Browser reload, token refresh, API pause or lost acknowledgement must never start another capture.

Display capture, native snapshot, encryption, publication and transfer as separate stages. During maintenance, say that live polling is unavailable and retain the last timestamp; do not show a stalled request as failure or a cached success as current health. Reconnect to the same operation after normal authentication becomes available. A failure with held services must identify the console recovery action and exact operation, not offer a generic retry. Completed ciphertext publication enables off-appliance download; downloading is not a restore test. Preserve the source until the operator explicitly removes an artifact through an ownership-checked action.

**Fresh target:** existing console enrollment establishes the new encrypted data disk, network and target disk recovery material. Add an explicit `RECEIVE BACKUP` choice at `host-ready`. It temporarily enables a narrowly scoped HTTPS receiver on the selected enrolled interface; it must not provision application databases or seed a new realm. Firstboot currently has no runtime TLS identity at `host-ready`—[TLS creation belongs to bootstrap](../appliance/nebulalog_manager/bootstrap.py)—so this receiver needs its own bounded-lifetime, FIPS-compatible TLS identity and a qualified console-to-browser trust bootstrap. Show the certificate fingerprint on the trusted console and verify it before entering a pairing secret; no blanket certificate-warning bypass, plaintext HTTP or `insecure` mode.

Pair once using a random console-displayed secret submitted in a same-origin POST, never in a URL. Retain only its hash server-side, bound to target installation, purpose and expiry. Exchange it for a Secure/HttpOnly/SameSite=Strict session with CSRF and origin checks. Rate/concurrency limits and explicit console renewal apply. It authorizes encrypted input delivery and redacted progress only. It is not a replacement Administrator/MFA grant and cannot authorize arbitrary host changes. Expiry/reboot closes network access while retaining owned partial ciphertext for explicit resume.

The browser selects configuration ciphertext, recipient certificate, encrypted PKCS#8 recovery key and, when chosen, the complete existing log-set directory. After transfer, the operator enters the key passphrase only at the hidden console prompt. Reuse `recovery_media.py`'s bounded PBES2/PBKDF2-HMAC-SHA256/AES-256-CBC admission and certificate/key match; do not send the passphrase or plaintext key through browser state, JSON, URLs, logs or argv. Unlock only for preparation/apply on private encrypted scratch; ordinary cleanup removes the temporary key, and crash handling identifies retained scratch without claiming physical erasure.

Inert preparation authenticates CMS, checks the full log set and exact source/runtime/policy link, computes complete space requirements, and returns a host-owned immutable review. It performs no database restore, listener activation or ordinary provisioning. Compare the backup digest against the independently retained backup receipt; copying the displayed digest alone proves no origin. Console confirmation binds target hostname, source isolation, scope, plan digest and complete input identity. Applying the approved plan enters the existing coordinator. Browser and console show the same operation/status; a network disconnect never causes redispatch. Restored passwords, MFA, recovery codes and roles remain unchanged. `runtime_ready` remains distinct from final login/forwarding/baseline/integrity/disk-recovery acceptance.

The running appliance's Restore view guides this actual fresh-target workflow and can show artifact/compatibility information. It must not suggest live overwrite is implemented. Supporting fresh recovery is not permission to reset MFA, skip firstboot or lower the required security baseline.

## Narrow proposed contracts

These routes are proposed, not existing APIs. Settle the coordinator contract before adding UI callers.

| Proposed control | Authorization and effect |
| --- | --- |
| `GET /api/recovery/capabilities`, recipient/job/artifact lookup | Current Administrator session; bounded redacted projection and explicit unavailable reasons. Authorize ownership independently on every lookup. |
| `POST /api/recovery/recipients` | Qualified step-up for enrollment/replacement; one bounded public certificate, fingerprint, expiry and opaque ID. No private key on the source appliance. |
| `POST /api/recovery/plans` | Administrator, exact-origin JSON; scope, recipient/artifact ID and explicit budgets. Host supplies measurements, installation/resource/code revision, expiry and digest. No paths, SQL, URLs or executable fields. |
| Step-up begin/callback relay; `POST /api/recovery/jobs` | Fresh trusted host plan at begin and completion; original authenticated browser/session binding; host-verified one-use grant; idempotency key. Fixed worker dispatch after durable acceptance. |
| `GET /api/recovery/jobs/{id}`, explicit resume/recovery/cancel | Authorized persisted operation. Status never acts. Effectful resume/recovery/cancel needs a newly checked action binding; it cannot replace inputs or replay uncertain effects. Reauthentication can recover the same subject's job through explicit fresh authorization, not by weakening session-bound plan ownership. |
| Recipient/artifact transfer admission and binary object ranges | Separate purpose-scoped session, exact artifact/object identity and quotas; never a credential-bearing download URL. The normal API may mediate authorization, but root/private artifact paths are not mounted into it. |
| Fresh receiver pairing/transfer/status | Console-enabled target-only session; no dependency on the absent Keycloak realm. Apply remains an exact local console confirmation, with browser progress. |

The host must independently verify issuer signatures, reviewed host audience/ACR, current Administrator role, original and step-up session validity, plan/action/resource binding, expiry and replay protection. Wire `StepUp.Begin/Complete` and the existing grant ledger rather than treating serialized `StepUpEvidence` as authority. Issuer outage fails new authorization. Check immediately before the first disruptive effect; the already accepted durable continuation must survive its own intentional Keycloak/API pause. Define and test that transition explicitly so recovery neither requires a now-stopped issuer nor extends a bearer grant indefinitely. Uncertain pre-dispatch state requires a fresh authorization/review.

Use one fixed host worker adapter for configuration capture and one for full-set capture, backed by the current coordinators and their lock ordering. Store an immutable child-operation mapping before effects; return/recover the same child on lost acknowledgements. Reuse encrypted `PrivateRecords`/grant/idempotency primitives where they fit, but keep large transfer inventories out of the small monolithic host-job ledger. Do not reinterpret the lifecycle hook dispatcher as an arbitrary browser executor. Registry/schema changes need explicit migration/invalidation and source-provenance updates.

## Current source boundaries

The recovery coordinator now separates authenticated preparation from explicit apply. Its console/media paths display a fresh-target review before final confirmation; the CLI exposes `--prepare-fresh` and `--apply-plan`. Preparation checks factory image/source compatibility, restored certificates and capacity, and does not install restore ownership or change application services. Apply binds the exact review and repeats checks; duplicate apply is status-only. This implementation still needs native roundtrip qualification.

`recovery_plans.py` provides reusable read-only sizing observations and per-filesystem phase budgets, with unknown duration unless comparable throughput evidence is supplied. `recovery_transfer.py` provides bounded resumable ciphertext object storage, owner/session bindings, durable range acknowledgement and structural admission of encrypted key material. These modules are included in the host source catalog. They do not expose an HTTP receiver, establish authentication, authorize a backup/restore, reserve space, or prove a sealed upload is an authenticated recovery set. Long file verification belongs in a durable host job. The independent host authority, fixed worker, public-recipient registry and protected browser routes remain to be implemented; see [RECOVERY_CONTROL_DESIGN.md](RECOVERY_CONTROL_DESIGN.md).

## Protected large-set delivery

Keep the current authoritative transport: configuration CMS, `logs/manifest.cms`, and indexed `logs/chunks/NNNNNN.cms`. Its limit is 256 MiB plaintext per encrypted chunk, at most 262,144 chunks, 64 MiB plaintext manifest and 64 TiB native archive; these are format bounds, not demonstrated capacity. Copy only ciphertext/certificate/encrypted-key inputs through the receiver. Existing restore still requires a full verified native plaintext archive on encrypted disk; do not promise zero plaintext disk use.

Implement resumable binary uploads in small fixed transport segments (for example 4 MiB, two in flight), distinct from the 256 MiB encrypted archive chunks. The host issues opaque transfer/object IDs from a fixed name/index inventory; reject arbitrary names, path separators, duplicate keys, symlinks, special files, overwrite, gaps, overlapping ranges, size overflow and unbounded multipart bodies. Enforce count, object and aggregate ceilings before writing and continuously during writes. Stream with bounded buffers and pinned no-follow descriptors onto proven LUKS/XFS private staging. Hash each completed object, fsync file and directory, then atomically acknowledge its exact identity. Lost acknowledgements reconcile by identity, not append/retry guesses. Page inventory/status responses and persist bounded checkpoints so 262,144 chunks never become one response or millions of in-memory segment records.

An uploaded manifest/receipt is untrusted transport metadata until authenticated CMS and exact set/link checks succeed. Do not mark import complete merely because all HTTP uploads succeeded. Finalization rejects extra/missing/reordered/truncated/substituted files and freezes the owned input set. Only the root coordinator receives pinned artifact handles resolved to its private files; the web request never supplies a root path. Recovery key material is excluded from source exports and downloaded log packages; upload of the separately escrowed key accepts encrypted PKCS#8 only. Backups remain recoverable only if that key is actually escrowed—an operator checkbox is an attestation, not a successful recovery test.

For export, provide one browser action for the complete set, not hundreds of thousands of manual downloads. Use a deterministic, stored-only ZIP64 *ciphertext transport wrapper*, streamed from frozen source objects, with a durable offset/checksum index for HTTP range resume; do not materialize another multi-TB archive. Its contents are only the fixed ciphertext files and public certificate/receipt. Import validates this constrained wrapper incrementally into the same object store (no generic `extractall`, compression, scripts, arbitrary paths or embedded private keys). The authenticated inner CMS format remains recovery authority. A directory-save path may reuse the same object protocol where browser capabilities are qualified, but it cannot be the only path without a declared and tested browser support policy. New wrapper/range parsing is a real implementation and negative-test item, not an assumed library guarantee.

Do not use `response.blob()`, `File.arrayBuffer()` on a whole set, JSON/base64 archives, or plaintext browser decryption. Binary helpers must preserve session fencing while allowing `application/octet-stream`, range semantics and cancellation. Short-lived HttpOnly purpose cookies can authorize ordinary streaming downloads without a secret in the URL; bind them to the current authorized actor/artifact, expire/revoke them, and reauthorize resumptions. Cache-Control/no-referrer, log redaction and no third-party content apply to both receiver and download pages.

Closing a browser cancels transfer requests only. Discarding an unsealed upload removes only exact owned temporary files after writers close; it never touches source media, completed backups, native jobs or holds. Once a coordinator owns the artifact, transfer cleanup cannot delete it. Active native cancellation and hold release require the coordinator's verified phase-specific recovery interface; no UI action should unlink a pointer or assert cancellation from a deadline alone.

## Plans, estimates and capacity

Move existing read-only observations into reusable host plan functions; do not copy their safety arithmetic into React. Use PG catalog sizes/configuration inventory, CH `system.parts` metadata, native archive inventory, `statvfs`, and existing [successful NewPart growth measurements](../internal/api/operations.go). No 100M-row scan is needed. Include age, sampling window and uncertainty. A plan expires or changes when installation/runtime/table/policy/recipient/input identity or required free space changes; repeat checks at dispatch and expensive phase boundaries.

Current source requirements to expose accurately:

- Configuration capture reserves at least `3 × measured configuration-plus-PG bytes + 1 GiB`, within its 20 GiB plaintext limit. Fresh configuration restore currently requires `3 × ARCHIVE_LIMIT + 1 GiB` regardless of the actual input size.
- Native backup reserves `2 × maximum_archive_bytes + max(table_bytes, 1 GiB) + growth_reserve_bytes`, then retains at least the selected free reserve, which must be at least 10 GiB and 10% of the data filesystem. The maximum archive budget must cover observed table bytes plus the existing margin. The adapter explicitly reports no hard native quota.
- Unseal needs the complete native archive plus bounded ciphertext/plaintext chunk and manifest scratch. Native restore additionally plans `maximum_archive_bytes + 2 × logical_native_bytes + 1 GiB`, with the same minimum filesystem reserve. Incoming ciphertext, retained configuration inputs, prior recovery artifacts, service copies and restored table can coexist. Compute peak occupancy across phases and filesystems; neither summing unrelated peaks nor showing only archive size is accurate.

Report capture pause, native backup, encryption, transfer, authentication/hash verification, native restore and integrity-check time separately. Existing code has budgets, not measured ETA. Record bytes and monotonic phase durations from completed operations and actual transfer progress; offer measured ranges only for comparable image/version/storage data. With no baseline, show unknown duration and an explicitly labeled operator-supplied throughput scenario. Never derive backup speed from EPS or promise a fixed compression ratio. Growth reserve uses measured arrivals over the planned hold duration plus spool/merge uncertainty; deletion holds mean retention cannot be assumed to free space.

The current native deadline range is 60–86,400 seconds. A measured multi-TB plan exceeding that bound must be refused visibly; completing the full scope requires a qualified longer-lived/per-phase observation design and safe timeout recovery, not silently clamping the estimate or resetting a deadline on every resume. Native reserve monitoring and settled failure/cancellation handling are required before enabling unattended full captures; the existing no-hard-quota indication is not a safety proof.

## Implementation order and validation

1. **Settle host contracts first.** Refactor current backup/restore preflight into reusable plans; finish and qualify the new settled-outcome retirement/recovery contracts, running-native cancellation, stable redacted progress, and frozen artifact references. Extend `backup.py`, `recovery_set.py`, `configuration_restore.py`, `log_backup.py` and focused tests under their current owners. Keep CLI and console using the same implementation. Do not change the CMS format or relax fresh-target guards.
2. **Build protected control and transfer.** Extend `internal/hostcontrol`, host operation/job primitives and fixed recovery adapters; add bounded transfer storage/transport and console receiver lifecycle. Wire the qualified step-up flow/store/host grant verifier through `internal/auth` and recovery handlers in `internal/api`; separately implement console pairing for the fresh target. Install only through the fixed host catalog/systemd/SELinux/Quadlet and provenance workflow. Do not copy modules into an enrolled appliance or expand the read-only socket implicitly.
3. **Connect both operator surfaces.** After contracts settle, add the Admin recovery page, binary helpers, job reconnect/status, complete-set download and the separate pre-runtime upload entry; extend `console.py` with receive/status/confirm/resume. Update `FIRST_BOOT.md` and `BACKUP_RESTORE.md` with the actual supported flow. Existing optical/local-path paths remain available. No UI was edited by this audit; apply the relevant UI skill and existing visual conventions when that work starts.
4. **Prove the whole workflow.** Unit/contract tests must cover roles, stale session/review, wrong/missing/replayed grants, broker/OTP/recovery behavior, origin/CSRF, duplicate JSON/headers, plan changes, paused services, reconnect and idempotency. Transfer tests need bounded memory, range retries, out-of-order/replaced files, archive parser limits, full disk, disconnect/restart, fsync boundaries, expiry, ownership and secret/log redaction. Coordinator tests need wrong key/corrupt input before effects, pending native return, uncertain effect refusal and only verified hold release. Run native Rocky x86_64 full browser → backup → off-appliance transfer → fresh target → existing MFA/RBAC/settings/certs/retention/logs/API/forwarding round trip, including interruptions, then final setup and compatible update/rollback recovery. Record actual hardware, data size and timing; small mocks do not close the 100M-record or native acceptance gates.

There is no architectural choice that needs Wayne to unblock this source plan. At execution, the operator chooses configuration/full scope, recipient, off-appliance destination and explicit reviewed budgets; console authority selects the fresh target and enables its temporary receiver. Native TLS/bootstrap, supported browsers, real fresh-MFA behavior, fixed-host provenance, resource reserve and recovery failure qualification remain engineering gates. No acceptance is claimed by this document, and the current low T9 reserve permits no native workload for this audit.
