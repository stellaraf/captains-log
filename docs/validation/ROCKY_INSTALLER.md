## Failed first Linux build and diagnosis

The original Kickstart post script rejected Packer's RSA authorized key because it contained a single terminal newline. The error was `Build requires a per-build RSA public key`. The FIPS setup command had returned successfully; the build user and random inaccessible password had already been created, and the authorized-key directory was empty. No appliance file provisioner or container bootstrap ran.

The exact key's SHA-256 was compared privately with the build public key, without displaying the key. The public-key encoder chain explains the terminator: [QEMU plugin v1.1.6](https://github.com/hashicorp/packer-plugin-qemu/tree/v1.1.6) uses the [Packer SDK v0.6.10 communicator](https://github.com/hashicorp/packer-plugin-sdk/tree/v0.6.10/communicator), whose authorized-key serialization includes one terminal LF. The corrected Kickstart accepts exactly that terminator and validates a single canonical RSA wire key with a 3072–8192-bit modulus. Embedded controls, duplicate command-line fields and malformed or additional key material are refused. The FIPS settings are unchanged.

A hash-verified, narrowly scoped recovery script completed only the remaining build-key/sudoers/SSH configuration in the disposable installer target, and the guest was rebooted. Its installed kernel booted with `fips=1`, but incorrect SELinux file labels and failed audit, D-Bus, time, login and SSH services prevented host provisioning. The aborted installer had not completed normal finalization. This manually recovered image is rejected as a release input; it does not prove a clean automated installation.

The failed builder was stopped. Its generated OS disk was checked offline by `qemu-img check` with zero metadata check errors, hashed, and its stopped failed OS image removed after the remaining read-only Docker filesystem-cache descriptor was identified. No shared VM or other workload was stopped. Host space reclamation may lag while that cache retains the inode. SHA-256 was `261efcd48011e5dfebb2da426d5857b036c1c6d299e518007e02c224f715c403`; file size was 3,681,026,048 bytes. Disk-image structural consistency did not establish operating-system health. The untouched blank data image, source inputs, sanitized receipt, serial/build logs and diagnostic screenshots were retained privately under `.local/appliance-build`.
