# Sealed-image cleanup and free-space sanitization

A successful guest sealer is necessary but does not prove a distributable disk is clean. Deleting SSH host keys, build accounts, random seeds, or temporary files leaves their old bytes in free filesystem blocks. The Rocky installer also retains Kickstart records and journals. An obsolete, disabled kdump image can retain its own hostname and machine ID inside a nested squashfs filesystem even after the normal initramfs has been rebuilt.

Preserve the original sealed export and a private checkpoint. Run the following phase on a **new standalone copy of the system disk**, in a disposable Linux builder. The log-data disk is never an input. Bind the original image read-only in the supervising mount namespace; `sanitize_image.py` checks the actual read-only filesystem flag. Before QEMU opens it, the wrapper inspects the [QCOW2 header and extensions](https://www.qemu.org/docs/master/interop/qcow2.html) and refuses backing files, external data files, encryption and snapshots. Give the job its own scratch filesystem, at least twice the system disk's virtual capacity plus a 16GiB free-space reserve, and a bounded service with no access to host block devices or networking. Use `KillMode=control-group` so the supervisor also contains tool descendants. Do not disable the `virt-sparsify` temporary-space check.

1. Qualify the exact installed distro `libguestfs`/`virt-sparsify` version with deliberately deleted markers in every XFS filesystem, swap, and a freed LVM extent. After **copy-mode** sparsification, read the entire virtual disk and require all markers to be absent. Verify retained file contents, modes, extended attributes, filesystem identities and swap UUID. Keep tool package/signature evidence and source/output hashes. Trimming or in-place sparsification is insufficient: our fixture retained all seven deleted XFS markers after an otherwise successful in-place run.
2. Supply the trusted installed-payload manifest captured from the frozen source. `artifact_cleanup.py` verifies an unconfigured, sealed appliance, a locked root account, removed builder enrollment and SSH keys, empty data state, and neutral active host identity. It refuses linked cleanup targets, hard links, foreign-owned targets, enabled or boot-referenced kdump images, changed files, and unexpected action scope. The fixed distro `/var/log/README` documentation symlink is preserved and checked. The guest sealer explicitly stops and disables kdump before clearing identity; the installer service selection alone did not leave it disabled in the measured native build.
3. The cleanup plan removes build Kickstart/history scripts, unused kdump images, and the six fixed `/etc/{passwd,shadow,group,gshadow,subuid,subgid}-` account backups left by builder-account deletion. The live account databases remain intact. It truncates existing build log files while preserving their owner, group, mode and extended attributes. It retains and checks all supplied frozen payload hashes and normal/rescue boot-image hashes. The exact plan and before/after metadata are written to the private job directory before proceeding.
4. `sanitize_image.py` runs copy-mode `virt-sparsify` with `--check-tmpdir=fail`, watches scratch free space, and stops only its own process group on a guard failure, including descendants whose leader has already exited. It opens the private pending output read-only, explicitly mounts all separate filesystems, keeps swap inactive, re-verifies the cleanup plan and retained controls, and proves the source and read-only output hashes did not change. Only after these checks does atomic no-clobber publication expose the final output path; failed intermediates remain in the protected work directory for diagnosis.
5. Audit the finalized disk for active and embedded identities, boot files, firmware/ESP requirements, blank log-data disk, and release trust/provenance. Package only that exact verified image. Import the resulting OVA into a new test VM, generate fresh per-instance identity, and perform first-boot and runtime checks. Filesystem cleanup, packaging, hypervisor import, native boot, cryptographic qualification and update acceptance remain separate results.

Example on the isolated Linux builder (paths are job-owned files, not host devices):

```sh
python3 appliance/packer/sanitize_image.py \
  --input /source/sealed-system.qcow2 \
  --expected-sha256 SOURCE_SHA256 \
  --output /scratch/output/sanitized-system.qcow2 \
  --work-dir /scratch/runs/sanitize-one \
  --payload-manifest /inputs/installed-payload-manifest.json
```

For a reviewed legacy qualification image, `--approved-plan` additionally binds every action to its approved path, action, original size and SHA256. This is a documented build derivation; it does not retroactively make an older frozen sealer reproducible.

`sanitization-receipt.json` records the exact source and output hashes, cleanup/control counts and final read-only verification. It is build provenance, not a signature or a substitute for the tool qualification fixture. Copy-mode sparsification does not promise to erase arbitrary partition-table gaps; audit the actual fresh-build layout and preserve bootloader/GPT regions. The normal/rescue images and all payload controls must remain unchanged by cleanup. Native firmware, FIPS self-tests, TPM enrollment and automatic encrypted reboot require their own acceptance evidence.

The 2026-09-09 native tooling qualification passed with Rocky `virt-sparsify 1.52.2`, `libguestfs 1.54.0`, and `qemu-kvm-core 10.1.0`; all nine deleted markers disappeared, all seven controls and their root ownership/modes/xattrs remained, and swap UUID/source hashes/read-only output hashes matched. The supervisor kept host block devices hidden, networking disabled and capabilities empty. Rocky's supermin base archive contained RPM-builder ownership, so its temporary extraction used GNU tar's documented [`--no-same-owner`](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html) through the tool-only `TAR_OPTIONS` environment. This did not change the signed archive or target-disk ownership.

Product-disk sanitization, final packaging/import, and the new EFI candidate remain pending until their explicit runtime receipts exist.
