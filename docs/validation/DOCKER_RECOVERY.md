# Development Docker storage shutdown and recovery

Observed **2026-09-08 UTC** on the shared macOS development host. This is development-runtime evidence, not a Rocky appliance, OVA, or production recovery qualification.

Docker Desktop requested a controlled engine shutdown at **08:13:54** after rotating its host-side `vm/init.log` failed with `ENOSPC`. The guest reported shutdown complete at **08:14:01**, and the virtualization process reported a graceful stop at **08:14:36**. ClickHouse metadata requests timed out and the development API subsequently refused connections. Docker's old control processes remained, with no VM or active restart. The separate Colima VM continued running.

Host free space rose from approximately 1.5 GiB to 16 GiB during the shutdown. No build-cache prune or file deletion was performed by this task; the measurements do not establish which mechanism released that space. The retained appliance-build directory occupied approximately 4.59 GiB. Its failed blank VM disks occupied only 1.39 MiB, and the service image archives shared hardlinks with the retained v6 bundle. Removing their older links would not recover the shared archive bytes.

The supported `docker desktop restart --timeout 45` failed in its quit phase because the stale Desktop processes did not exit. After independently verifying that Docker's VM had stopped and that the only remaining VM belonged to Colima, recovery sent `SIGTERM` to the exact old Docker process identities. The sole remaining stale supervisor was terminated after that grace period and Docker Desktop was reopened. No disk reset, volume removal, image deletion, global prune or Colima lifecycle action was performed.

The new Docker VM started at **08:23:56**, and the backend changed from starting to running at **08:24:12**. Its startup log had no new storage-exhaustion or fatal VM error through the independent **08:24:56** check. Free space was approximately 11 GiB after startup; a running Docker engine does not establish sufficient headroom for a complete appliance build and scale benchmark.

All four existing NebulaLog containers had restart policy `no` and remained stopped. The development [`docker-compose.yml`](../../docker-compose.yml) now specifies `restart: unless-stopped` for PostgreSQL, ClickHouse, Keycloak and the application. The same policy was applied to those existing containers, then Compose started them without rebuilding or recreating them. Configuration validation passed; inspection confirmed every policy and unchanged image identity. PostgreSQL and ClickHouse started at **08:25:23**, followed by Keycloak and the application at **08:25:28**. No unrelated project's containers were manually started.

The actual `/api/health` response subsequently reported application, PostgreSQL, ClickHouse and DNS healthy, authentication configured, and the collector listening. Its version remained **`0.1.0-dev.44e2eb18f7cd`**. Metadata queries resumed and persisted native Traffic, DNS-derived Threat, URL, Data Filtering and System records had post-recovery ingestion timestamps. A bounded source audit at **08:30:37** counted **168,098 native PAN-OS records with zero native parser failures**, plus **345,741 unrelated non-PAN-OS records** retained as unknown. See [PALO_REAL](PALO_REAL.md) for that category distinction.

These observations prove service recovery, persisted records, renewed ingestion and configured restart policies. They do **not** prove uninterrupted delivery or zero log loss during the outage, a fresh human MFA login, automatic recovery on a subsequent daemon restart, or production first-boot/backup/restore behavior. A second shared-daemon interruption was not introduced merely to test the policy. The [full release gates](../RELEASE_ACCEPTANCE.md) remain open.

Private local receipts retain the bounded process/engine observations and category counts without credentials or raw log payloads. Docker's original host/backend, virtualization and guest-console logs remain the authoritative shutdown/startup evidence.
