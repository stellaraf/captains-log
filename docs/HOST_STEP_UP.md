# Host-control identity candidate

Source review and local tests: **2026-09-08**, pinned to **Keycloak 26.7.3**. This is a separate, disabled definition in [`host_identity.py`](../appliance/nebulalog_manager/host_identity.py), plus a GET-only configuration verifier. It is not installed in the ordinary development realm or called by appliance bootstrap. It does not enable `AssurancePolicy`, a callback route, a host authorization grant, or a host job. A successful configuration read-back always reports `qualified: false`.

The definition makes the candidate concrete enough for an isolated qualification fixture. Production assurance remains blocked on the authentication paths described below. The built-in password authenticator does not attest that a password was stored locally, and overriding a client's browser flow does not disable the realm's broker endpoints. These are explicit boundaries of the candidate, not a permanent restriction that external administrators cannot manage the appliance.

## Separate client and flow

| Setting | Candidate |
| --- | --- |
| Realm and issuer | Existing `nebulalog`, exact `https://<installation-dns>/realms/nebulalog` |
| Client and authorized party | `nebulalog-host-control`; confidential, `client-secret` authentication |
| Access-token audience | Exactly configured custom audience `nebulalog-host-control`; application role does not add the ordinary application audience |
| Browser return | One exact HTTPS URI, `/api/host/step-up/callback`; no wildcard, alternate origin, CORS origin, or post-logout redirect |
| Authorization | Code flow with required S256 PKCE and required authenticated PAR |
| Other grants | Implicit, password, service account, device, CIBA, JWT authorization, standard token exchange and external token retrieval disabled |
| Refresh and scopes | Refresh issuance disabled; no default/optional client scopes, including `offline_access` |
| Lifetime | Access-token and dedicated client-session maxima 120 seconds |
| Required ACR | Exact `urn:nebulalog:host-control:local-mfa:v1`, mapped to LoA `2`; the same value is the client's minimum and default |
| ACR reuse | LoA Max Age `0`; entire password-plus-factor flow belongs to that level |
| Role scope | Only existing, non-composite `nebulalog` client role `ADMINISTRATOR`; mapping carries a user's actual scoped role and never grants it |

The fragment contains three flow representations with stable import identifiers, one LoA configuration, the client and its role-scope mapping. When using the Admin REST API instead of realm import, an explicitly authorized provisioner must create flows first and replace the client's browser binding with the returned flow ID. A confidential-client secret must be generated and stored separately in protected runtime storage; the definition contains no secret or user. Neither creating a new user nor resetting an existing password is part of this contract.

The realm's default browser flow, ordinary application client, normal broker post-login flow and enrollment required actions remain unchanged. The candidate's browser override is:

```text
nebulalog-host-local-mfa-v1
  CONDITIONAL credentials
    REQUIRED Condition - Level of Authentication [LoA 2, Max Age 0]
    REQUIRED Username Password Form
    REQUIRED second-factor
      ALTERNATIVE OTP Form
      ALTERNATIVE Recovery Authentication Code Form
```

There is no Cookie, Kerberos, Identity Provider Redirector, conditional OTP exemption, or passwordless alternative. The LoA condition's parent-success callback records level `2` only when that entire parent flow succeeds, and Max Age `0` records it for the current authentication instead of reusable authentication history. This is the proposed meaning of the ACR, contingent on qualification of the complete issuer configuration. [26.7.3 LoA authenticator](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/authentication/authenticators/conditional/ConditionalLoaAuthenticator.java), [26.7.3 ACR store](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/authentication/authenticators/util/AcrStore.java).

Factor executions deliberately remain alternatives inside a **required** subflow. A required OTP execution can schedule enrollment when the account lacks OTP; enrollment during that same login must not count as use of a previously enrolled factor. In the candidate, an unconfigured alternative cannot use that required-execution enrollment branch, and the subflow needs a successful alternative. A removed credential, no credential, exhausted recovery codes, `Try another way`, cancellation and required-action transitions still require actual browser testing. A used recovery code must also be proved unusable a second time. Realm OTP settings do not retroactively change existing credentials: Keycloak validates stored credential subtype, algorithm, digits and period. Qualification must inspect those non-secret credential metadata for existing administrators and cover legacy HOTP, SHA1 and different-period factors before claiming exact TOTP/HMACSHA256 semantics. [26.7.3 stored-credential validation](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/credential/OTPCredentialProvider.java). [26.7.3 execution and enrollment behavior](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/authentication/DefaultAuthenticationFlow.java), [26.7.3 flow guidance](https://github.com/keycloak/keycloak/blob/26.7.3/docs/documentation/server_admin/topics/authentication/flows.adoc).

The default ACR client attribute is a single delimiter-encoded string, **not** a JSON array. The ACR-to-LoA map is JSON. The client minimum prevents a weaker nonessential request from lowering the configured requested level, but returned assurance must still be checked. [26.7.3 client attribute encoding](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/AbstractClientConfigWrapper.java), [26.7.3 ACR resolution](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/utils/AcrUtils.java).

## Exact returned-claim contract

The client has exactly five direct mappers and no inherited scope mappers:

- A custom audience mapper adds the host-control audience to the access token and introspection response.
- The built-in ACR mapper derives `acr` from completed authentication level; no hardcoded ACR, user attribute, upstream assertion or generic MFA flag substitutes for it.
- The user-session-note mapper maps `AUTH_TIME` to whole-number `auth_time` in ID/access tokens.
- The built-in subject mapper includes `sub` in access tokens.
- A client-role mapper reads actual scoped `nebulalog` roles into `resource_access.nebulalog.roles`. Its explicit role scope contains only `ADMINISTRATOR`, and the read-back refuses a composite administrator role or any extra role scope. This emits the role only when the user actually has it. [26.7.3 client-role mapper](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/mappers/UserClientRoleMappingMapper.java).

`amr` is intentionally absent. An authenticator reference mapper's session history is not an independent per-factor freshness attestation. Acceptance must use the exact qualified ACR, not guessed AMR values. ACR labels have no universal numeric ordering; the verifier accepts only the named value. [26.7.3 ACR mapper](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/mappers/AcrProtocolMapper.java).

For an `openid` code exchange, Keycloak 26.7.3 generates the ID token and `at_hash`. Its ID-token payload `typ` is `ID`; access-token payload `typ` is `Bearer`. The ID token's session identifier and expiration are copied from the access token, its authorized client follows the requesting client, and its nonce comes from the authorization session. Require valid signatures and the expected algorithm, exact issuer/audience/authorized client, signed ID nonce, `at_hash` binding to the returned access token, and equality of ID/access `sub`, `sid`, `auth_time` and `acr`. A missing `sid` must fail; transient sessions can omit it when refresh issuance is disabled. Do not replace it with a browser value or `session_state`. [26.7.3 token creation](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/TokenManager.java), [26.7.3 code-exchange response builder](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/grants/OAuth2GrantTypeBase.java).

`auth_time` reflects session authentication completion and can derive from a broker authentication time. It is not the time of an independently attested local second-factor execution. Validate it against transaction start with UTC-second precision, the trusted current time and the two-minute deadline; fresh `iat` alone is insufficient. Signed `sid` provides correlation, not present revocation status. Claims do not attest an approved plan, operator confirmation, resource revision, issuer reachability or a live role assignment. [26.7.3 authentication/session handling](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/services/managers/AuthenticationManager.java).

## Browser and API integration contract

1. The authenticated Administrator requests step-up for an already computed and reviewed operation plan. The API allocates a bounded, one-use, server-side transaction containing original application issuer/subject/session, operation, plan digest, installation/resource revision, creation time, exclusive deadline, random state and nonce, and a random PKCE verifier. Browser input must not supply assurance policy or invent the server-owned plan binding.
2. The API sends an authenticated PAR POST to the fixed issuer endpoint `/protocol/openid-connect/ext/par/request`, using the confidential client credential and the parameters returned by `authorization_parameters`. Those parameters are `scope=openid`, `response_type=code`, `response_mode=query`, exact redirect, S256, `prompt=login`, `max_age=0` the matching `acr_values` hint, and an essential exact ID-token ACR claim. State, nonce and challenge are unpadded base64url values representing 32 bytes. No user password or second factor passes through the Captain’s Log API.
3. Require the PAR endpoint's successful response, a bounded `urn:ietf:params:oauth:request_uri:` value and a positive, bounded expiry. The API accepts PAR lifetimes up to 1,200 seconds but clamps the pending transaction to the earliest of its 120-second maximum, PAR expiry, original actor/session expiry, operation binding expiry and review expiry. The browser receives only the fixed authorization URL with `client_id` and `request_uri`. Neither the request URI nor authorization parameters are an authorization grant. Failed or ambiguous exchanges are not automatically retried. [26.7.3 PAR endpoint and request URI generation](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/par/endpoints/ParEndpoint.java), [26.7.3 PAR route](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/par/endpoints/ParRootEndpoint.java).
4. The callback consumes only the exact pending transaction. Bind its unpredictable state to the browser session and compare issuer, verify signed nonce, exchange the code server-side using the saved verifier and exact redirect, then enforce the token contract above. Reject refresh tokens, duplicate/ambiguous fields, protocol errors and oversized responses; bounded unknown token-response metadata is ignored. The newly authenticated subject must equal the original subject. Its Keycloak session **may differ** from the original application session because the dedicated flow does not reuse the cookie authenticator; retain both identities privately without claiming equality.
5. Recompute or reread the plan and current installation/resource revision before any host authorization. Consumption must be atomic and once only under concurrent callbacks. Neither a callback nor a bearer token alone authorizes a host job. A later host bridge must independently validate the narrowed grant, human role/session, exact operation and digest, expiry/revocation and replay protection before its first effect. Issuer outage and revocation behavior remain release gates.

Keep token bodies, client secrets, PKCE verifier, nonce, session IDs and callback query strings out of URLs other than the required protocol exchange, logs, public user JSON and ordinary job records. The callback page must have no third-party assets, no referrer leakage, no caching and an immediate redirect to a clean application URL. These are integration requirements, not implemented routes in this Python module.

## Read-back and remaining blockers

`verify_read_back(get, hostname)` accepts a caller-owned, GET-only trusted TLS transport. It verifies the server's exact version, realm TLS/enrollment/OTP settings, all three scoped flow IDs, all nested execution sequences and configurations, the separate client's grant/URI/PKCE/PAR/lifetime/ACR settings, all five mappers from both client and mapper endpoints, empty default/optional scopes, the one exact existing administrator role scope, and separation from ordinary client/broker flow bindings. OTP replay protection must be explicitly enabled with `otpPolicyCodeReusable=false`; a missing flag does not pass read-back. It rejects extra mappers, additional attributes other than a bounded Keycloak-generated secret-creation timestamp, missing read-back fields, duplicate identities, condition changes, factor enrollment substitutions, normal-login bindings and another Keycloak version. The returned receipt contains a definition digest and fixed qualification requirements, never a secret, session or enabled assurance policy. The Admin REST flattening rules are tied to the pinned source. [26.7.3 authentication management API](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/services/resources/admin/AuthenticationManagementResource.java).

This verifier checks the dedicated configuration's shape. It does not certify arbitrary realm-wide client policies, custom provider binaries, other flows, broker mappers, user storage or a concurrent later administrator change. Its receipt is deliberately insufficient for policy admission. Qualification needs an immutable image/configuration evidence bundle plus a live drift/revocation strategy.

The unresolved cases are concrete:

- **Broker endpoint isolation:** Keycloak's direct broker login endpoint accepts an authentication session independently of the browser flow and finishes through the provider's own post-login path. Removing a redirector or hiding social buttons does not prohibit it. The candidate records LoA only after full local-flow success, so the intended negative behavior is refusal or a lower, unaccepted ACR when a broker path skips that flow. This must be proved for existing/first broker login, linked accounts, IdP hints, direct endpoint navigation, upstream MFA/ACR claims and required-action/account-linking transitions. The current definition does not assert that a client's browser override alone prevents broker token issuance. If an accepted ACR can be reached without the required local challenge, qualification must stop and a reviewed client-scoped broker guard or authenticator is necessary. [26.7.3 broker endpoint and completion handling](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/services/resources/IdentityBrokerService.java).
- **Local credential provenance:** the built-in username/password form uses Keycloak's credential manager, which can validate through user storage providers. A completed password form is not proof of a locally stored password. A linked broker account with a local password may work; an external/LDAP administrator without one cannot be silently accepted or described as supported. The initial local fixture needs independently verified account/credential provenance, while the product still needs a reviewed path for every supported identity method. If locally stored credentials must be proven atomically by the issuer in a mixed-storage realm, the present built-ins/profile are insufficient and a reviewed provider or equivalent issuer-enforced invariant is required. [26.7.3 username/password validation](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/authentication/authenticators/browser/AbstractUsernameFormAuthenticator.java).
- **PAR realm binding:** the pinned PAR implementation stores entries under `par:<random-id>` without the realm in that cache key. Do not treat possession of a PAR handle as independently proving the originating realm. Exact issuer/client, signed nonce, saved PKCE verifier and pending transaction bindings remain mandatory, and swapped/cross-realm handles need a negative fixture test. This observation is from the pinned implementation; it is not a claim that PAR alone qualifies this installation. [26.7.3 PAR cache insertion](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/par/endpoints/ParEndpoint.java).
- **Qualification matrix:** repeat a successful challenge within the same second and later in the same SSO session; remove or change ACR/max-age parameters; use ordinary app tokens, ID tokens, direct/implicit/device/service/exchange grants, stale authentication with fresh tokens, absent/exhausted factors, pending credential reset, different subject, wrong session, expired/canceled/replayed transaction, changed plan/revision, disabled/revoked user/session/role, issuer outage and concurrent callbacks. Verify no host effect occurs throughout. Explicitly show both local OTP and one-use recovery success, then fail the used recovery code and the just-used TOTP (including a code used for the preceding ordinary login). Keycloak checks OTP reuse through its single-use store when code reuse is disabled. [26.7.3 OTP replay check](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/credential/OTPCredentialProvider.java).

No ephemeral realm, user, secret, container, image, frozen guest or host job was created for the source tests. Tests use synthetic Admin REST representations and configuration mutation cases. They establish fail-closed configuration checks, not the behavior of a running Keycloak instance. Provisioning an isolated fixture is a separately coordinated step after this definition is reviewed.
