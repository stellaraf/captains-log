# Verified session evidence for future host control

Source review and local tests: **2026-09-08**. Private verified-session evidence and the pure assurance-policy check are included in frozen candidate v6. Subsequent [server-side step-up transaction work](HOST_STEP_UP_TRANSACTIONS.md) and the disabled [identity candidate](HOST_STEP_UP.md) are later source changes. None exposes a host mutation endpoint, issues an authorization grant, changes the live Keycloak configuration, or qualifies the running guest.

## Implemented contract

The existing middleware still verifies bearer signatures, issuer, application audience and expiry with the configured OIDC verifier, then determines the same client-scoped Captain’s Log role. `auth.Current(ctx)` and the public `User` JSON remain exactly `id`, `name`, and `role`. A separate context key holds an opaque `VerifiedSession` extracted from that same verified token. Neither the bearer token nor its raw claims are retained in this value. `CurrentSession(ctx) (VerifiedSession, bool)` returns false for malformed or oversized evidence; missing optional assurance claims may return a parsed session, which the policy subsequently refuses.

`VerifiedSession` exposes internal accessors for issuer, subject, authorized client, session ID, authentication time, issuance/expiry, audience, ACR and AMR. Slice accessors return copies. Its JSON serialization returns an error and standard formatting is redacted. The session ID is for a future protected binding implementation only; never add it to `/api/me`, browser responses, URLs, ordinary audit/job records, or logs. Missing/invalid extra claims leave existing application login/RBAC behavior unchanged. An unavailable verifier fails authentication instead of panicking.

`AssurancePolicy.Check(session, now) error` is deterministic and performs no network requests or mutations. Successful evaluation means only that this verified token's bounded claims meet a supplied local policy at the supplied time. It does **not** establish Administrator authorization, a live/unrevoked session, current issuer availability, possession beyond the bearer token, a user-confirmed operation, or host authorization. Existing `Require("ADMINISTRATOR", ...)` remains independently necessary.

There is no application configuration or default policy that enables this check for host work. Its zero value refuses every session. The API, host controller and deployment wiring remain future work.

## Strict claim profile

The secondary session parser limits verified payloads to 32 KiB, JSON nesting to 16 levels and values to 4,096. It rejects duplicate names at every nesting level, including escaped duplicate names. Unknown claims are structurally checked within those limits and discarded. Oversized or structurally ambiguous session evidence cannot qualify for assurance, even if the existing role parser accepted the token.

| Claim | Parsing and use |
| --- | --- |
| `iss`, `sub` | Nonempty exact strings; cross-checked against the verifier's issuer and subject. Issuer has a 2,048-byte cap; other retained strings have a 512-byte cap. Control characters, invalid Unicode/replacement characters and leading/trailing whitespace are refused. |
| `aud` | Nonempty string or array of distinct strings, at most 16. Cross-checked against the verifier's audience list. Policy requires the exact configured audience to be present; additional audiences do not substitute for it. |
| `azp` | Optional at parsing, required by policy as an exact authorized-client match. Audience membership alone does not establish which client requested the token. |
| `sid` | Optional at parsing, required and nonempty for policy. No fallback to browser input, subject, token ID, or legacy `session_state`; no assumption that a signed session ID is currently active. |
| `auth_time`, `iat`, `exp`, `nbf` | Whole positive UTC epoch seconds only, up to year 9999. Strings, fractions, exponent notation, zero/negative values, overflow and contemporary millisecond timestamps are refused. `iat`/`exp` are required and cross-checked with verifier times; `auth_time` is additionally required by policy. `nbf`, when present, receives the policy's stricter future-time check. |
| `acr` | Optional at parsing; policy requires membership in an explicit set of exact, case-sensitive accepted values. No numeric ordering, wildcard, substring or automatic meaning for `1`, `2`, `gold` or any other label. |
| `amr` | Optional array of distinct strings, at most 16; scalars/null/mixed arrays are invalid. When the policy names required methods, every exact method must be present. An empty policy method list is permitted only alongside a reviewed accepted ACR; it cannot authorize AMR-only inference. |
| `typ` | Keycloak's payload token-type string, distinct from the JOSE header `typ`. Policy requires an explicit exact type; a future reviewed Keycloak bearer policy should require `Bearer`, not accept an ID or refresh token as equivalent evidence. |

This is deliberately a narrower privileged-evidence profile than general JWT/OIDC parsing. Normal application authentication is not newly restricted to this profile. The pinned `go-oidc` v3.21.0 verifier verifies the signature before parsing claims, checks audience membership but explicitly does not establish `azp`, and permits five minutes of `nbf` leeway. The separate check supplies client binding and stricter time bounds without changing ordinary RBAC. [Pinned verifier implementation](https://github.com/coreos/go-oidc/blob/v3.21.0/oidc/verify.go).

## Explicit policy and refusal behavior

A policy must have `Reviewed=true`, a nonempty bounded `ReviewID`, an unexpired `ReviewExpiresAt`, an exact HTTPS issuer without credentials/query/fragment, audience, client ID, token type, and at least one accepted ACR. `ReviewID` identifies an external review of the actual issuer flow and mapper configuration; neither a string nor the boolean proves that review occurred. This configuration must come from the administrator-controlled installation policy, never from request JSON or token claims. Re-review it when the issuer version, client scopes, mappers, authentication/broker flow or assurance semantics change.

Authentication age, token age and token lifetime must each be explicitly positive and at most 15 minutes. These are maximum implementation bounds, not enabled product defaults. Choose shorter values during the actual policy review. Optional clock skew is 0–30 seconds and only tolerates a clock ahead of the evaluator; it never extends token expiry or freshness. Expiry and age limits are exclusive: equality to expiration or a maximum age is refused. Authentication cannot occur after issuance, expiry must follow issuance, and `nbf` must precede expiry. A refreshed token with recent `iat` and old `auth_time` is refused.

Errors are stable exported sentinels suitable for `errors.Is`: `ErrAssurancePolicy`, `ErrSessionClaims`, `ErrSessionBinding`, `ErrSessionTime`, and `ErrAssurance`. They contain no claim values, session IDs, bearer tokens or upstream response bodies. Policy admission is separate from establishing a supported UI reauthentication flow; callers must not turn refusal into an automatic bypass.

## Pinned Keycloak meanings and review requirements

The appliance's FIPS Keycloak [Containerfile](../appliance/images/keycloak-fips/Containerfile) and [BOM](../appliance/images/keycloak-fips/BOM.json) currently pin **26.7.3**. Older development notes about 26.3.3 are not evidence about the new image. The following conclusions use official versioned sources, not inferred vendor defaults:

- OIDC `iat` records token issuance; `auth_time` records authentication. A refresh must preserve the original authentication time instead of replacing it with the new issuance time. ACR is a context identifier whose meaning the parties agree upon; AMR names methods rather than their individual execution times. [OpenID Connect Core, token claims and refresh semantics](https://openid.net/specs/openid-connect-core-1_0.html#IDToken), [AMR registry semantics](https://www.rfc-editor.org/rfc/rfc8176).
- Keycloak's basic client scope maps `auth_time` from the `AUTH_TIME` user-session note. [26.7.3 OIDC scope/mappers](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/OIDCLoginProtocolFactory.java).
- Authentication completion updates that note for non-SSO authentication; when present, `AUTH_TIME_BROKER` can supply its value. SSO preserves the previous value. Therefore an `auth_time` claim alone does not prove a fresh local MFA challenge or the instant at which the second factor was completed. [26.7.3 authentication/session handling](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/services/managers/AuthenticationManager.java).
- Keycloak's ACR mapper derives the configured level of authentication and maps it to ACR. Its fallback can produce `0` for SSO or `1` for other authentication; neither value is accepted by an implicit application default. [26.7.3 ACR mapper](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/mappers/AcrProtocolMapper.java).
- The AMR mapper reads completed authenticator references from user-session notes and places the configured references in a token. That is no independent per-factor freshness attestation. `amr:["mfa"]`, a generic `mfa:true`, upstream claims or a successful broker assertion are insufficient without the exact reviewed issuer policy. [26.7.3 AMR mapper](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/mappers/AmrProtocolMapper.java).
- The access token receives its session ID from the Keycloak user session and its authorized client from the requesting client. This creates a signed binding identifier, not evidence of present session validity. [26.7.3 token creation](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/TokenManager.java).

The versioned step-up guidance supports a reviewed flow with required authenticators, explicit ACR-to-LoA mapping and controlled LoA reuse time. A LoA condition with Max Age 0 is documented as valid for the current authentication only; `acr_values` alone is a nonessential request. Parameters traveling through a browser can be modified, so a future flow must validate the returned assurance and bind the authorization transaction; evaluate PAR or signed request objects as part of that design. [26.7.3 authentication flow guidance](https://github.com/keycloak/keycloak/blob/26.7.3/docs/documentation/server_admin/topics/authentication/flows.adoc).

**Inactive definition:** [the separate host step-up candidate](HOST_STEP_UP.md) now defines a disabled confidential PAR/code/PKCE client, whole-flow local password plus existing OTP/recovery LoA condition, narrow audience and actual administrator-role scope, and exact GET-only configuration read-back. It is not wired into bootstrap or the main development realm, and read-back always reports unqualified. Broker endpoint isolation, local credential provenance, pinned browser behavior and session/revocation semantics remain explicit qualification blockers.

**Current limitation:** no deployed host-control flow has been reviewed or qualified to bind this ACR to the required recent local MFA across ordinary login, refresh, SSO, recovery, local-account and broker paths. Existing mandatory OTP for application login and broker post-login remains important, but is not automatically an action-specific step-up guarantee. The assurance policy must remain unavailable until that evidence exists. In particular, do not infer trusted MFA from an upstream SAML authentication context or relabel an imported broker claim with the accepted ACR.

## Future wiring and acceptance

Application wiring should obtain the session only from `CurrentSession` after the existing middleware, enforce Administrator access, evaluate the installation-owned reviewed policy with a trusted current clock, and invoke a separate narrowly specified host-authorization protocol. It must not serialize this context as a grant. The host must independently validate a host-control audience, human/client/session binding, exact operation and reviewed plan digest, installation/resource revision, expiry and one-use replay protection at acceptance and before the first effect. Define how current session revocation and issuer outages affect acceptance; the pure check makes no online validation call. Preserve an independent local recovery path.

The signed-token tests use synthetic ES256 JWTs and the real pinned OIDC signature verifier, without contacting or changing any tenant. They cover valid retention and public-user redaction; wrong signatures/issuers/audiences/expiry; malformed types, duplicates, nesting and size; all three unchanged RBAC roles; missing session identity/authentication time; wrong `azp`/token kind; old authentication with fresh tokens; time boundaries/skew; generic and unreviewed MFA-looking claims; and absent/expired/invalid policy. These are local source tests, not step-up browser or guest qualification. No [host bridge](HOST_CONTROL_INTEGRATION.md) or [release acceptance](RELEASE_ACCEPTANCE.md) gate is closed by this change.
