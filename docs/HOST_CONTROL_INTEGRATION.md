# Host management integration audit

Original source inspection: **2026-09-07**, working tree based on `44e2eb18f7cd`; updated **2026-09-08 after frozen candidate v7** for the [read-only storage plan slice](HOST_READ_ONLY_PLANS.md). This audit makes no running-guest or release-qualification claim. It identifies the gap between the [full specification](SPECIFICATION.md) and existing browser/API/host code. Capabilities, `storage.grow` review creation and owner-bound lookup now have a protected local transport and Administrator API source. The broader mutation interfaces below remain proposed. The [plan/job primitives](HOST_JOB_PRIMITIVES.md) provide the encrypted durable journal; no executor, host-verifiable authorization grant or dispatch integration is exposed.

The application currently performs several real application configuration operations, but it has **no privileged host mutation bridge**. Root-published observations are useful diagnostics, not appliance management. Normal administrators still lack browser workflows for storage growth, updates/recovery, backup/restore, baseline actions and post-install host configuration.

[API routes](../internal/api/server.go) now include the three read-only plan endpoints described below; no job/mutation endpoint is implemented. This source change is not a deployment receipt.

## Existing trust and observability limitations

- The host publishes sanitized schema-versioned JSON at `/run/nebulalog-status/status.json`; the API mounts that directory read-only. [Reader](../internal/api/appliance_status.go#L21) enforces ownership, safe paths/permissions, bounded schema and 90-second freshness. `/run/nebulalog-public/maintenance.json` is a **separate Apache-labeled directory**; do not merge the two mounts or relabel them together. Missing/unsafe/stale host data is unavailable, not a passed security check.
- Generic [ObservedPage](../web/src/Admin.tsx) renders commands as text and missing fields as “Not reported.” Next-candidate [freshness handling](../web/src/FreshHostObservation.tsx) suppresses cached host success after a failed fetch and after 90 seconds, including background-tab resume; failed evidence stays hidden through a pending retry until a current request succeeds. The dedicated [host storage panel](../web/src/HostStorageObservation.tsx) applies the same persistent failed-refresh state. A future management page must also disable plan confirmation when its evidence is stale. The public [health response](../internal/api/server.go) still reports updates `not_connected` independently of the newer authenticated snapshot.
- [Authentication](../internal/auth/auth.go#L71) verifies bearer tokens and application roles. Next-candidate [verified-session support](HOST_AUTHORIZATION.md) retains bounded private session/authentication claims and provides an explicit assurance-policy check. It has no enabled assurance policy, qualified step-up flow, independent host verification or action-bound grant. Existing Administrator guards and parsed claims alone are insufficient authorization for irreversible host jobs.
- [Apache maintenance](../appliance/httpd/nebulalog.conf.in#L29) currently rejects **all external `/api` and `/realms` requests** while active, including future job polling and renewed authentication. Recovery UI cannot be built assuming these routes remain reachable. Any exceptions must be narrow, authenticated and tested; forwarded client headers must never create a maintenance bypass.

## Proposed narrow typed job bridge

Keep the Go API unprivileged and the existing public snapshot read-only. The [new read-only plan source](HOST_READ_ONLY_PLANS.md) uses a dedicated root-owned Unix socket with bidirectional Linux peer checks and a separate control group. After an initial capacity block, its isolated Linux Python/Go round trip and unauthorized-peer checks passed with synthetic storage. Its installation, API mount, SELinux policy, real encrypted-guest observation and boot enrollment remain unimplemented/unqualified. Extend only after qualification; expose no Podman socket, shell, arbitrary service name, filesystem path, environment variable, URL-to-fetch or executable input. Peer identity establishes the caller process, **not the human's authorization**.

The host independently validates a short-lived, host-control-audience authorization from the configured issuer, including subject, client, Administrator role, session identity, expiry and recent MFA assurance. Add an explicit step-up flow with a reviewed Keycloak authentication policy; do not accept a browser-supplied `mfa:true`, generic broker claim or reused login screenshot. Bind the resulting one-use grant to the installation UUID, exact operation, reviewed plan digest, resource revision, session and expiration. Recheck at acceptance and immediately before first mutation. Viewer/Analyst remain read-only; management artifacts, plans and job details are Administrator-only unless an explicit safe summary is defined.

HTTP roadmap; only the three explicitly marked read-only rows have current source:

| Endpoint | Typed behavior |
| --- | --- |
| `GET /api/appliance/capabilities` | **Read-only source implemented:** single enrolled storage pool and current planning availability; execution remains false. Broader operations and assurance/configuration metadata remain future work. |
| `POST /api/appliance/plans` | **Read-only source implemented for `storage.grow` only:** re-inspected identity/geometry, immutable expiring review and digest. No grant or execution. Other operation reviews remain future work. |
| `GET /api/appliance/plans/{id}?digest=…` | **Read-only source implemented:** exact original owner/session/digest, expiry and fresh resource reinspection; no journal mutation. |
| `POST /api/appliance/jobs` | Plan ID/digest, action-bound grant, idempotency key and optional opaque secret/artifact handles. Return `202` with a durably accepted job ID; never wait in the HTTP request for host completion. |
| `GET /api/appliance/jobs[/{id}]` | Bounded redacted state/progress/evidence, actor, timestamps and recovery options. User authorization is checked on every read. |
| `POST /api/appliance/jobs/{id}/cancel` | Only queued/planning or an explicitly declared safe checkpoint. Once a disk/database mutation starts, finish/reconcile safely; do not kill a root subprocess as a generic cancellation implementation. |
| `POST /api/appliance/artifacts` | Separate bounded kinds for signed release bundles, configuration backups, certificate chains and reviewed content. Quarantine on encrypted storage; host assigns immutable opaque IDs and hashes after validation. Never accept client-selected paths. Secret uploads use dedicated short-lived handles, stay out of logs/argv/ordinary job JSON, and are destroyed after consumption. |

Initial operation schemas should be fixed enums, not a general command wrapper:

- `storage.grow` and `storage.add_disk`: host-issued disk/member IDs, observed size/serial/LUKS/PV/VG fingerprints and plan digest. Explicit destructive blank-disk confirmation and recovery-key escrow verification precede add-disk activation. Reinspect immediately before each irreversible stage; never offer shrink or automatic destructive rollback.
- `updates.check/install/rollback/finalize`, `os.apply`, `reboot.complete`: verified release/transaction IDs and qualified component transitions; never a public-key path or arbitrary image tag. Separate publisher enrollment with an independently authenticated fingerprint. No UI action may bypass signed-channel expiry/sequence/path checks, global transaction locks, maintenance or real health/MFA gates. Schedule edits use typed weekday/start/end/IANA timezone and distinct OS/component policy; scheduled jobs record a system actor and the explicitly authorized policy revision, not a fabricated human session.
- `backup.create`, `restore.plan/apply`: configuration backup by default; enrolled recipient ID and validated artifact ID. A restore plan must state exact database/configuration overwrite scope, source installation/version compatibility and identity effects. Apply only after qualified backup transport and live restore adapters exist; staged extraction is not restore success.
- `baseline.scan/review/select`: registered licensed-content/profile IDs, policy/assessment hashes and per-finding review data. Preserve machine failures, expiration and manual-evidence requirements. Keep remediation unavailable until a separate qualified plan specifies exact controls, conflicts, exceptions, reboot impact and verified recovery. Baseline switching must update dependent selection/assessment state coherently.
- `settings.network/time`, `certificates.activate`: bounded typed values tied to current configuration. Network changes require a checkpoint and timed confirmation from the new reachable endpoint; otherwise restore the previous configuration. Certificate changes stage complete validated material and test HTTPS/auth/Syslog/internal-client behavior before switching and after restart. Never weaken FIPS or certificate verification to pass a check.

## Durability, recovery and implementation order

Persist the authoritative host job journal on encrypted `/var/lib/nebulalog/manager/jobs`, with atomic records, fsync, per-job operation/request hashes and append-only audit. Mirror normalized job/audit metadata into PostgreSQL for the application, but a database outage or restore must not erase the host's record of an accepted operation. A repeated idempotency key with the same body returns the existing job; a different body is refused. Reconcile accepted-but-unacknowledged requests after API/host restarts.

Use one writer coordinator and the existing global manager transaction lock, with one defined lock owner per operation rather than nested acquisition of the same lock. Standalone backup/staged restore now acquire manager → first-boot → runtime → baseline nonblocking locks; they invoke only primitives that do not reacquire the global lock. Baseline browser operations still need compatible global serialization before exposure. Journal intent before effects and evidence after effects; recovery inspects reality and resumes only supported owned stages. A completed component update stays committed if maintenance release alone fails. Expose `recovery_required` and a fixed retry-finalization action rather than repeating activation or restoring a database automatically.

Keep the edge available for a deliberately scoped job-status/recovery experience during maintenance. Design and test how already authorized job reads work while API writers or Keycloak restart, how expired sessions behave, and how a user regains authenticated recovery access. A short-lived job-specific read grant may be appropriate if ordinary authentication is temporarily unavailable, but it must disclose only that job's redacted status and authorize **no mutations**. The local console remains the independent recovery route. Do not simply exempt `/api` or `/realms` from the current gate.

Implement in this order: **(1)** capability/status contracts and fresh-auth/session support; **(2)** host-issued read-only plans, durable job/audit/secret-artifact primitives and recovery visibility; **(3)** qualified existing operations such as scan and reviewed storage growth; **(4)** signed update delivery/finalization and reboot flows; **(5)** complete backup/restore, post-install network/time/certificates and baseline changes/remediation. Each mutation remains disabled until its actual guest adapter and failure recovery pass.

Acceptance must include all roles, expired/replayed/wrong-session grants, changed plans/disks/artifacts, concurrent OS/storage/update jobs, API/issuer/database outages, process/power failure at every stage, interrupted reboot, exhausted staging, stale status, failed maintenance release, secret/log redaction and real browser reconnection. Retain before/after guest evidence and data/authentication parity. This document does not close any [release acceptance](RELEASE_ACCEPTANCE.md) gate.
