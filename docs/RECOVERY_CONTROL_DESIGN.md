# Recovery control: authority and durable dispatch

Decision and implementation status, 2026-10-19. The inactive authority core and challenge storage now have bounded source tests; no callback, authorization policy, host grant service, recipient enrollment or worker is enabled. The full scope and 154 acceptance requirements in [RECOVERY_WORKFLOW_PLAN.md](RECOVERY_WORKFLOW_PLAN.md) remain unchanged, including Okta/Entra users, local OTP/recovery, native recovery, interrupted work, transfer, and update/rollback. Synthetic evidence is not a substitute for issuer, browser or native qualification.

## Schema 4 initialization status

The v2 pending table now has an explicit schema 4 source identity. Revisions 1–3 and their SQL hashes remain unchanged. The lifecycle adapter reconstructs the complete schema 4 catalog from fixed SQL and requires both pending tables, exact ownership/constraints/indexes and the existing retention/delivery holds. Only a same-revision update or rollback is described for schema 4; the sole enabled cross-revision operation remains 1→2. `CURRENT_REVISION` remains 3.

[`fresh_database.py`](../appliance/nebulalog_manager/fresh_database.py) is an **inactive PostgreSQL initialization primitive**. Its future firstboot caller must own the protected runtime journal and lock and verify installed factory/source/image provenance. The typed binding and journal dictionaries do not themselves authorize work. Initial admission requires an empty PostgreSQL 17.11 application database. The caller durably checkpoints the installation, source, image, schema, PostgreSQL system identifier and database OID before the single fixed DDL transaction. Expected catalog reconstruction and public DDL run as the unprivileged application owner. A lost acknowledgement retains the original intent: only the same empty database or exact schema 4 can resume. An existing catalog cannot mint an initialization intent, and a completed retry cannot recreate an emptied database.

This primitive is included in the fixed host source catalog but has no command, bootstrap hook or service. Its protocol and SQL composition tests do not execute PostgreSQL. Real PostgreSQL creation/resume/refusal tests remain required. So do firstboot lock/journal wiring, independent ClickHouse/retention stages, and a restored-data catalog-only path. PostgreSQL completion must not release maintenance or start identity/edge services. The existing restore call to `_migrate(initialize_retention=False)` cannot become permission to initialize schema 4; that flag currently only suppresses policy configuration.

Provenance capture, installer staging, release assembly and installed enrollment explicitly refuse schema 4 until these integration and exact image/restored-authentication gates are qualified. Source recognition alone does not permit packaging or activation. Full backup/log restore support for schema 4 remains pending, including all existing K01–K03 acceptance requirements and native update/rollback testing.

## Decision: root owns the challenge and the action boundary

Use a separately versioned, fixed recovery socket, not an extension that silently changes `plans.sock`. Preserve its peer verification pattern and add independent human verification. Control frames contain typed IDs/digests/budgets, never paths, URLs, SQL, executable names or service selectors. Token exchange frames have a separate bounded shape: at most three 64 KiB tokens plus bounded metadata, capped at 256 KiB. Ordinary control replies remain at most 64 KiB. Do not put those tokens into the current 16 KiB `HostJobs` proof argument; pass a short opaque host-owned proof handle instead.

Proposed internal interfaces (not public routes or installed commands):

```text
RecoveryControl.review(actor, operation, typed_parameters) -> owned_plan
RecoveryControl.challenge(original_bearer, plan_id, plan_digest,
                          action, request_digest) -> HostChallenge
StepUp.Begin(ctx, freshly_looked_up_plan, HostChallenge) -> start
StepUp.Complete(ctx, state, code, freshly_looked_up_plan) -> private_pair
RecoveryControl.prove(challenge_id, original_bearer, id_token,
                      access_token) -> private_proof_handle
RecoveryControl.accept(plan_id, digest, idempotency_key, proof_handle) -> job
RecoveryWorker.observe(job_id) -> retained_status
RecoveryWorker.dispatch(job_id) -> checkpointed_result
```

`HostChallenge` contains a host-generated UUID and 256-bit nonce, canonical actor/session hashes, installation, exact operation and operation-schema version, action, plan ID/digest, resource revision, request digest, policy generation, creation time and exclusive expiry. Persist it on encrypted root-owned storage before PAR. The host supplies this nonce to the API; the browser cannot choose it. Extend the PostgreSQL pending record and strict `StepUpBinding` to retain the exact challenge identity/action/request binding. OAuth state and PKCE verifier remain API-generated. The host re-verifies the ID token's signed nonce against its own challenge and its `at_hash` against the access token, both subjects/sessions/times/ACR, and the independently verified original application token. API completion must retain the token pair only for the private transport; do not make `StepUpEvidence` JSON-serializable or use a boolean verdict.

The challenge UUID becomes `VerifiedGrant.id`. The existing ledger atomically records grant consumption with job acceptance. Proving a challenge does not consume it or accept work; the verifier must not take the manager lock recursively. Read challenge/proof records through a lock-owned verifier context, and reject mismatched action/request/actor/resource/policy. Repeated proof submission for the same challenge returns identical short-lived grant metadata with fresh live checks; it cannot mint another grant ID. Actor hashes use the established Go JSON-array domain encoding; Python stores these as opaque hashes and does not re-encode identity claims.

The current challenge journal retains up to 1,024 issuance/replay identities, with 64 active globally, eight active per actor/session, and 16 issuances per actor/session in five minutes. It refuses when full. Deleting expired identities would let old request IDs mint new nonces, so automatic pruning is not implemented. A fresh cancellation-review protocol is also required: HostJobs can cancel an accepted job after its original plan expires, while the present challenge/step-up binding requires an unexpired review window. These lifecycle limits must be resolved before enabling a service; operators must not clear the journal or invent new plan expiries.

`migrations/host_stepup.sql` remains byte-identical to the qualified schema 1/2/3 source. New DDL lives separately in `migrations/host_stepup_v2.sql`; the release schema validator deliberately refuses that combined source until a new schema revision and native migration/rollback are qualified. Restore quarantine clears both pending tables atomically. No current release declaration silently adopts the new table.

Implement the cryptographic/live-verification core in Go beside `internal/auth`, reusing its strict parser and maintained OIDC verifier. A fixed root-invoked helper, proposed `cmd/nebulalog-host-authorizer`, receives bounded private stdin and returns a bounded redacted decision; it takes no request-selected executable, issuer, trust store or path. Python owns plans and journals, not a second hand-written JWT implementation. The helper must be independently installed and bound to the selected measured host generation: running the API's copy or accepting an API-signed verdict would defeat the boundary. Existing host payloads contain source scripts and have an 8 MiB per-file cap; native-binary build/source receipts, exact size admission, signed artifact binding, catalog/dispatcher, SELinux and factory/update integration are explicit work, not assumed to fit that format today.

## Live issuer authority and policy admission

Use the exact enrolled HTTPS issuer with mandatory certificate identity, fixed backchannel routing, no redirects/proxies or request-selected endpoint, bounded response parsing, and finite total decision time. Independently validate original and step-up bearer signatures, issuer, audience, authorized client, type, times and the target's restore token cutoff. At challenge creation check the original session; at proof/acceptance and immediately before first effects check **both** original and new sessions and current Administrator membership. Token refresh may retain the same original `sid`; a new login/session cannot adopt its pending challenge.

For the pinned candidate, use `GET /protocol/openid-connect/userinfo` separately with each exact bearer, require success and the same verified subject, and discard other user information. Keycloak 26.7.3's endpoint performs session/client/user checks plus realm/client/user not-before and token revocation checks. This is the proposed online validation path, subject to fixture verification. An Admin REST session listing alone is insufficient: its implementation enumerates sessions rather than performing those token checks. Ordinary app tokens do not carry the host-control audience; do not enable introspection without audience checks to work around this. [Pinned UserInfo implementation](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/endpoints/UserInfoEndpoint.java), [session listing](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/services/resources/admin/UserResource.java), [introspection audience checks](https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/protocol/oidc/AccessTokenIntrospectionProvider.java).

Current effective application-role membership comes from the root-owned read-only inspector via the exact user and `users/{subject}/role-mappings/clients/{enrolled-application-client-uuid}/composite` Admin REST read. [`bootstrap.py`](../appliance/nebulalog_manager/bootstrap.py) already provisions `nebulalog-appliance-inspector` with `view-users`, `view-clients`, `view-realm` and uses effective-role read-back. Verify its installation ownership and exact roles; never use the API's write-capable identity-manager credential. Role reads and online token checks must be fresh, uncached authorization evidence; oversized, missing, malformed or unavailable evidence refuses. Validate actual permissions and effective group/composite changes in the pinned fixture. Source SAML group changes are reflected through the configured broker synchronization, not magically through a local role read; require qualified reauthentication/role synchronization and revocation behavior for Okta and Entra rather than promising instantaneous upstream deprovisioning.

Admit an assurance policy only from protected installation enrollment referencing exact image/provider, complete relevant issuer configuration and behavioral qualification evidence. Read-back drift, changed version/flow/mappers/client policy/broker/user-storage behavior, missing review, expired review or issuer outage blocks new actions. The current disabled candidate and a hand-written `Reviewed` flag are insufficient. Broker/federated users are not permanently excluded: qualify their real path or implement an issuer-enforced challenge that covers them; do not relabel upstream claims as local MFA. Ordinary login remains unchanged until its own explicit reviewed migration.

## Callback relay and secrets

The current web entry always initializes normal Keycloak login. Add a separate minimal callback entry that does **not** do that. Use an explicit-user-opened window so the parent keeps its original in-memory application session. The GET callback only validates bounded unique `code/state/iss` (or a bounded error), removes the query immediately, and relays to the initiating same-origin window with exact target origin. The parent checks origin, exact window reference and pending transaction, then sends an authenticated same-origin POST using `authenticatedFetch(..., expectedSession)`; the server again checks the original session and the fresh host plan before `Complete`. No OAuth completion or host proof is issued by the unauthenticated GET. A missing opener, changed session, canceled/blocked window or expired state ends that attempt; explicit retry creates a fresh challenge, never re-exchanges the code.

Apply strict origin/CSRF, duplicate-header/parameter/body limits, no-store/no-referrer, a dedicated restrictive CSP and no third-party assets. Exclude callback queries and secret body/header fields from Apache/API traces before enabling the route. Keep state, nonce, verifier, tokens and proof handles out of browser persistent storage, public jobs, ordinary audit and URLs except the required OIDC parameters. Browser reload may lose a pending challenge safely; accepted jobs remain durable. Qualify popup/window restrictions and accessible browser behavior before claiming support.

Short-lived proof credentials, if needed across asynchronous acceptance/dispatch, live only in a separately protected encrypted secret spool with the original exclusive expiry, never in ordinary job JSON or configuration backup. Fail closed after restart/expiry unless an already-started child is reconciled. Delete/revoke spool entries after the start boundary, failure or expiry; background cleanup is bounded. Invalidate challenges/proofs, PostgreSQL pending transactions and API pool secrets on restore/re-enrollment/policy rotation. Preserve consumed-grant/audit evidence instead of restoring it as live authority.

## Durable start, continuation and recovery

Extend the exact job journal through an explicit schema version; do not reinterpret old `accepted_pending_dispatch` as executable. Preserve old records and refuse migration with unresolved work. Reserve one job/child UUID, immutable recipient revision, output/artifact identity, budgets, accepted host generation and request digest **before** any coordinator effect. Add an inert `FullBackupManager.prepare_owned(...)`/`run_owned(...)` boundary (names proposed) so acknowledgement loss cannot allocate a new child; configuration-only capture needs the same durable mapping/admission discipline. Never recover by calling today's `create()` again with a guessed path or a new UUID.

The fixed systemd worker outlives API/Keycloak and dispatches only the named coordinator adapter. Admission returns the durable job ID; a bounded worker pickup rechecks current plan/resources/recipient, selected code, expiry and both live sessions/current role immediately before the first disruptive action. A queued job whose proof expired moves to `authorization_required`, not automatic execution. Use one lock owner: `PrivateRecords` already holds `manager/transaction.lock`, while backup children acquire manager → firstboot → runtime → baseline and full backup has a distinct parent lock. Release the short job-ledger lock before entering a child; a persistent ownership/fence plus the coordinator's own locks protects dispatch. The final authorization barrier must execute inside that child admission boundary, not before an unbounded queue or lock wait.

Journal `dispatch_intent` and child identity before effects, and a durable child start/authorization receipt at the guarded boundary. After that boundary, continuation and safe settlement of that **same** child use its durable authority and reality checks; they must survive the operation's intentional issuer/API pause. They do not require a fresh bearer at every stage or authorize changed inputs/new work. On restart, a proven unstarted child needs fresh authorization; an uncertain started child is reconciled, never replayed. Revocation after dispatch prevents new jobs/changes, not essential cleanup of already started work. Explicit operator resume/retire or safe pre-dispatch cancellation uses a new action-bound grant and exact owned job; native running cancellation remains separately qualified, never a process kill.

Job lookup after normal reauthentication may use a fresh current Administrator check for the same stable issuer/client/subject plus explicit read authorization; do not rewrite the original session owner. A takeover/effectful continuation is a separately audited action binding. During maintenance leave Apache's API/realm gate intact: the browser shows last observation and reconnecting, then reconciles the same job. The console remains the independent recovery channel. Status does not dispatch, release holds or infer success from elapsed time.

## Recipient and registry lifecycle

The inactive `recovery_recipients.py` storage component now has source tests. It stores one bounded public X.509v3 certificate per immutable recipient UUID/revision, its PEM hash, DER fingerprint, typed request binding and escrow acknowledgement. It accepts RSA 3072/4096 with exponent 65537, current validity, non-CA constraints and key-encipherment usage; it refuses private-key material, unsupported critical extensions and unsupported key purposes. A real public-key check and CMS probe use the shared explicit RSA-OAEP/SHA-256/MGF1-SHA-256 and AES-256-GCM profile. These checks establish local compatibility, not certificate-chain trust, key possession or native FIPS qualification. The registry retains at most 64 recipients and 128 mutation events, then refuses new mutations without pruning replay history.

No controller or browser enrollment is enabled. The persistence API's typed binding is not authority: enrollment and disabling still require a reviewed action and fresh MFA from the future qualified host controller. It must show the certificate fingerprint and bind the current registry revision before committing. Existing root CLI validation (`x509 -checkend` plus the public encryption probe) does not establish this full enrollment policy. Source export never contains the private key.

Replacement creates a new ID with revision 1; never replace bytes beneath a plan or retained backup. Disabling appends a retained event and blocks new lookups. Exact mutation retries return the original result, while current lookups still reject disabled or expired recipients. Registry genesis is installation-owned and retry-safe; missing/corrupt initialized state refuses rather than recreating. Final dispatch must look up the exact recipient/hash under the shared owned lock before capture; this worker integration is pending. Already-started work uses its pinned recipient copy and safe settlement. Backup and restore integration must retain public registry metadata as historical material under the new installation, with explicit re-enrollment for new capture; that integration is also pending. Never adopt old grants, job ownership or live transfer sessions.

Transferred inputs retain immutable transfer/object IDs and original owner binding. A changed application session requires explicit verified adoption; do not edit owner fields. Frozen structural ciphertext becomes a coordinator input only after an atomic ownership handoff that prevents transfer cleanup or mutation. Fresh-target pairing can deliver ciphertext and show redacted progress; it cannot enroll a running-source recipient or approve restore. The encrypted private key is unlocked only at the trusted console, and apply uses the exact prepared review/input/target binding.
